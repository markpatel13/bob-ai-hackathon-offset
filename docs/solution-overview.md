# Solution Overview

## What We Built

**Drug Safety Signal Detector** is an open-source, browser-based pharmacovigilance
tool that lets any user — from a professional drug-safety analyst to a curious
researcher — type in a drug name and immediately receive a ranked, statistically
grounded list of the reaction patterns that look unusually dangerous for that drug,
compared to the rest of the FDA's 20-million-report adverse-event database.

No enterprise license. No data download. No code required to operate.

## How It Works

The full pipeline runs automatically when a user submits a search:

1. **Query openFDA** — [`fda_api.py`](../src/fda_api.py) hits the openFDA
   `drug/event.json` endpoint and pages through up to 1,000 adverse-event reports
   for the requested drug. Optional date-range filters narrow the window.

2. **Normalise the raw JSON** — [`data_processor.py`](../src/data_processor.py)
   flattens the nested report structure into a tidy DataFrame of
   `(report_id, drug_name, reaction, received_date, serious, death, …)` rows.
   Each report can contain multiple drugs and multiple reactions; every
   drug-reaction combination becomes its own row.

3. **Calculate PRR for every drug-reaction pair** —
   [`prr_engine.py`](../src/prr_engine.py) applies the
   **Proportional Reporting Ratio** formula to every unique combination found in
   the fetched data:

   ```
   PRR = [A / (A + B)] / [C / (C + D)]

   A = reports with this drug AND this reaction
   B = reports with this drug AND other reactions
   C = reports with other drugs AND this reaction
   D = reports with other drugs AND other reactions
   ```

   A PRR > 2.0 means the reaction appears more than twice as often among reports
   for this drug as it does across all other drugs — the WHO-accepted threshold
   for a candidate signal.

4. **Detect and rank signals** — [`signal_detector.py`](../src/signal_detector.py)
   filters for pairs that cross the minimum PRR threshold (default: 2.0) *and* have
   a minimum number of supporting reports (default: 3), then ranks them by signal
   strength (PRR value). Each result is classified as **Weak**, **Moderate**,
   **Strong**, or **Very Strong**.

5. **Trend analysis** — [`trend_analysis.py`](../src/trend_analysis.py) groups
   the same filtered reports by calendar period (daily / weekly / monthly /
   quarterly) to show whether the reaction rate for a flagged signal is growing,
   stable, or declining over time.

6. **Plain-English summaries** — [`ai_summary.py`](../src/ai_summary.py) converts
   the raw PRR statistics for any selected signal into a clear, jargon-free
   sentence such as:

   > *"VIOXX shows a 4.7× higher rate of MYOCARDIAL INFARCTION than expected
   > based on 312 reports, meeting the threshold for a Strong safety signal."*

   Summaries are available in three styles (short, standard, detailed) and can
   optionally be generated by an LLM (Claude / GPT) for richer clinical context.

7. **Dashboard display** — [`app.py`](../src/app.py) (Streamlit) renders the
   ranked signal table, trend chart (Plotly), report-level data explorer, and
   plain-English summary in a single interactive web UI.

## Key Design Decisions

| Decision | Rationale |
|---|---|
| **Streamlit for the UI** | Zero front-end build tooling; the entire app is a single Python process. Ideal for a data-science prototype that judges can run with one command. |
| **openFDA as the only data source** | Free, real, government-verified data. No synthetic data, no proprietary feed, no account required. Judges can reproduce any result independently. |
| **PRR as the core metric** | PRR is the WHO-recommended standard for spontaneous reporting database signal detection. It is a single, defensible formula that is easy to explain and audit. |
| **Minimum count gate (≥ 3 reports)** | Prevents single-report artefacts from generating misleading infinite-PRR signals — a well-known pitfall in pharmacovigilance. |
| **Modular pipeline (one file per stage)** | `fda_api → data_processor → prr_engine → signal_detector → trend_analysis → ai_summary → app` makes each stage independently testable and replaceable. |
| **Rule-based summaries with optional LLM** | The app is fully functional with no API key. The LLM layer (`generate_llm_summary`) adds richer clinical context when a key is available, but is never a hard dependency. |
| **In-memory caching in Streamlit session state** | Avoids re-fetching the same FDA data on every widget interaction, keeping the UI snappy without requiring a database. |
